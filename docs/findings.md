# Findings

## 1. Overview

This document summarizes the primary findings from the OpenSSH authentication log analysis.

The findings are based on authentication records processed using **KNIME Analytics Platform**, deterministic analysis performed using **Python**, and experimental Security Operations Center (SOC)-style explanations generated by **Llama 3.2 through Ollama**.

Two main samples were evaluated:

1. A 50-record failed-authentication sample associated with source IP `59.63.188.30`.
2. A 50-record successful-authentication sample used to test the generalized final V5.1 pipeline.

The purpose of the analysis is to identify what can be directly supported by the available evidence while separating deterministic observations from LLM-generated security interpretations.

---

## 2. Dataset Findings

The original OpenSSH dataset contained:

```text
655,147 raw log records
```

KNIME processing identified:

```text
Failed password records:                   197,587
Accepted password/publickey records:           182
Combined authentication records:           197,769
Unique source IP addresses:                   1,042
```

The source IP with the largest number of authentication records was:

```text
59.63.188.30
```

This source IP was associated with:

```text
28,766 authentication log records
```

The first 50 records from this source IP group were selected for the primary failed-authentication experiments.

A separate 50-record successful-authentication sample was also exported from KNIME to determine whether the same Python and LLM pipeline could analyze a different type of authentication activity.

## 4. Syslog Repeat Finding

One of the most important findings was that the number of CSV records did not necessarily equal the number of authentication events represented by those records.

Within the 50-record failed-authentication sample:

```text
Ordinary authentication records:           25
Compressed repeat records:                 25
```

The compressed records contained syslog notation similar to:

```text
message repeated 5 times: [ Failed password ... ]
```

All 25 compressed records in the analyzed sample contained a repeat value of five.

Using the project's deterministic counting method:

```text
Ordinary events represented:
25 × 1 = 25

Repeated events represented:
25 × 5 = 125

Total authentication events represented:
25 + 125 = 150
```

Therefore:

```text
50 CSV records
=
150 represented authentication events
```

All 150 represented authentication events were classified as failures.

No successful authentication event was identified within this selected sample.

This finding demonstrates why the project uses Python rather than the LLM to calculate authentication activity.

## 6. Failed-Authentication Indicators

The evidence directly supports the following observations:

- Repeated failed password authentication activity occurred.
- The analyzed records involve source IP `59.63.188.30`.
- The analyzed records target the `root` username.
- The authentication method is `password`.
- The sample contains 50 CSV records.
- Twenty-five records contain compressed syslog repeat notation.
- The 50 records represent 150 authentication events under the project's counting method.
- All 150 represented authentication events are failures.
- No successful authentication event appears in the selected sample.
- The selected activity spans 6 minutes and 26 seconds.

These statements are treated as observations because they are derived from processed log evidence and deterministic Python calculations.

---

## 7. Failed-Authentication Security Interpretation

The concentration of repeated failed password authentication activity against the `root` account from one source IP within a short period is **consistent with possible brute-force authentication activity**.

However, the evidence does not establish the identity or intent of the person or system responsible for the source IP activity.

The evidence also does not establish that unauthorized access was successful.

The activity can therefore be described as potentially suspicious and worthy of investigation without claiming that a confirmed compromise occurred.

## 9. Successful Authentication Does Not Establish Authorization

A major interpretation limitation is that a successful authentication event does not automatically establish that the activity was legitimate or authorized.

The successful-authentication sample establishes that the selected records contain successful password authentication events.

It does not independently establish:

- Who controlled each source IP.
- Who performed each authentication.
- Whether each login was authorized.
- Whether an account had been compromised.
- The intent behind the activity.

For this reason, the project treats `SUCCESS` as an authentication result rather than proof of legitimate activity.

## 10. LLM Experimental Findings

The project found that Llama 3.2 became more reliable when its responsibility was reduced from calculating facts to explaining Python-verified evidence.

The experimental progression showed:

```text
V1/V2
Raw evidence + prompt engineering
→ Useful explanations, but factual and formatting problems remained.

V3
Python-verified facts + raw logs
→ Verified facts were available, but unsupported information
  could still be introduced.

V4
Structured Python evidence
→ Reduced hallucinations and improved evidence-based explanations.

V4.1
Expanded deterministic event counting
→ Correctly separated CSV records from authentication events
  represented by compressed syslog records.

V5
Generalized CSV input
→ Allowed the pipeline to analyze different KNIME-exported samples.

V5.1
Verified evidence + LLM explanation + numerical validation
→ Added deterministic checking of selected numerical LLM claims.
```

The experiments demonstrated that **prompt engineering alone did not guarantee factual accuracy**.

A more reliable approach was to calculate facts using Python and restrict the LLM primarily to explanation and interpretation.

## 11. Final V5.1 LLM Finding

During the final V5.1 successful-authentication experiment, Llama 3.2 received Python-verified evidence rather than being asked to independently calculate the authentication statistics.

The LLM correctly reported several important values, including:

```text
14 unique source IP addresses
5 unique usernames
50 successful authentication events
0 failed authentication events
password authentication
```

It also produced the requested SOC-style sections:

```text
AUTHENTICATION SUMMARY
TIMELINE
OBSERVED INDICATORS
SECURITY INTERPRETATION
RISK LEVEL
RECOMMENDED SOC ACTIONS
```

The LLM assigned:

```text
RISK LEVEL: MEDIUM
```

The risk level is an LLM-generated interpretation and should not be treated as deterministic evidence.

The final response also included general SOC recommendations. Some recommendations were broader than the supplied evidence, demonstrating that an LLM may still introduce generic security guidance even when the numerical evidence is correct.

## 12. V5.1 Automated Validation Finding

V5.1 introduced automated validation of selected numerical statements generated by the LLM.

For the final successful-authentication experiment, the validator reported:

```text
[PASS] Source IP count
Python verified: 14
LLM claimed: 14

[PASS] Username count
Python verified: 5
LLM claimed: 5

[NOT CHECKED] Total authentication events
Python verified: 50

[PASS] Successful authentication events
Python verified: 50
LLM claimed: 50

[PASS] Failed authentication events
Python verified: 0
LLM claimed: 0
```

The final summary was:

```text
Numerical claims checked: 4
Numerical inconsistencies detected: 0
```

All four numerical claims that could be automatically checked matched the Python-verified evidence.

The total authentication event value received:

```text
NOT CHECKED
```

This did not indicate that the value was incorrect.

Instead, the validator could not reliably extract that particular numerical claim from the wording used by the LLM.

This demonstrates an important limitation of deterministic validation: an LLM can express the same information in different ways, and a validator should not assume that it understands a statement when a reliable numerical claim cannot be extracted.

## 13. Automated Testing Finding

Automated unit tests were created for important deterministic portions of the project.

The tests evaluate areas including:

- Normal authentication event counting.
- Compressed syslog repeat counting.
- Different repeat values.
- Verified evidence calculations.
- Authentication result counts.
- Timeline calculations.
- Correct LLM numerical claims.
- Incorrect numerical claims.
- Numerical extraction behavior.

A specific test was added to ensure that an IP address such as:

```text
137.189.241.248
```

would not cause the validator to incorrectly interpret the final octet `248` as a username-count claim.

The final test suite produced:

```text
Ran 12 tests in 0.018s

OK
```

All 12 automated tests passed.

This provides additional confidence in the deterministic portions of the project, although it does not establish that every possible input or LLM response has been tested.

---

## 14. LLM Variability Finding

Another important finding was that LLM responses can vary even when the same verified evidence is provided.

Across experiments, the model could change:

- Numerical statements.
- Wording.
- Security interpretations.
- Risk levels.
- Recommendations.
- Compliance with requested formatting.

Later versions reduced these problems by limiting the model to Python-verified evidence and adding numerical validation.

However, V5.1 does not eliminate all possible LLM errors.

This supports treating LLM output as an analytical aid rather than authoritative evidence.

---

## 15. Deterministic Analysis vs. LLM Interpretation

The experiments demonstrated an important difference between deterministic processing and generative interpretation.

### Deterministic Python Analysis

Python is used for:

```text
record counting
repeat-message counting
represented event counting
SUCCESS / FAILURE counting
source IP counting
username counting
authentication-method extraction
timeline calculations
numerical validation
```

These calculations can be reproduced from the same input.

### LLM Analysis

Llama 3.2 is used for:

```text
summarization
security interpretation
SOC-style explanation
risk discussion
recommended analyst actions
```

These responses may vary between executions.

The project therefore treats Python-generated evidence as the factual source of truth and the LLM output as a supporting explanation that requires review.

---

## 16. What Cannot Be Concluded

The supplied evidence does not establish:

- The identity of the person or system responsible for the source IP activity.
- The intent behind the authentication activity.
- Whether a source IP is known to be malicious.
- Whether successful authentication was authorized or unauthorized.
- Whether successful unauthorized access occurred outside the selected evidence.
- Whether other authentication methods or accounts were targeted outside the selected samples.
- Whether the failed-authentication activity continued before or after the selected 50-record sample.
- Whether activity outside the successful-authentication sample contained failures.
- Whether an LLM-generated risk level represents a confirmed level of security risk.

These limitations are important because authentication evidence should not automatically be described as a confirmed attack, compromise, or legitimate login without additional supporting evidence.

---

## 17. Primary Technical Finding

One of the most important technical findings of the project is that **CSV record counts should not automatically be treated as authentication event counts**.

In the failed-authentication sample:

```text
50 CSV records
represented
150 authentication events
```

In the successful-authentication sample:

```text
50 CSV records
represented
50 authentication events
```

The difference was caused by compressed syslog repeat messages in the failed-authentication sample.

Deterministically processing these messages in Python prevented the LLM from having to estimate the number of represented events.

---

## 18. Primary LLM Finding

The project demonstrates that an LLM can assist with converting structured authentication evidence into a readable SOC-style explanation.

However, the experiments also demonstrate that:

> **Giving an LLM verified evidence does not guarantee that every part of its response will be correct.**

Prompt engineering reduced some problems, but deterministic preprocessing and validation provided stronger safeguards.

The final pipeline therefore does not make the LLM responsible for establishing the factual authentication evidence.

---

## 19. Final Finding

The primary failed-authentication analysis identified a concentrated sequence of failed password authentication activity targeting the `root` account from source IP `59.63.188.30`.

The selected 50 CSV records represented **150 failed authentication events** under the project's deterministic syslog repeat-counting method and occurred within an observed period of **6 minutes and 26 seconds**.

The activity is **consistent with possible brute-force authentication behavior**, but the available evidence does not establish malicious intent or successful unauthorized access.

The second experiment demonstrated that the generalized pipeline could also process a successful-authentication sample containing:

```text
50 successful authentication events
14 unique source IP addresses
5 unique usernames
0 failed authentication events
```

The final V5.1 validation stage successfully checked four numerical LLM claims, with:

```text
4 PASS
0 FAIL
1 NOT CHECKED
```

The project also completed:

```text
12 automated tests
12 passed
```

Overall, the experiments support the following approach:

> **KNIME structures the evidence, Python verifies the facts, the LLM explains the findings, automated validation checks selected claims, and a human analyst makes the final judgment.**

The project therefore demonstrates a practical way to use an LLM as a cybersecurity analysis support tool while keeping deterministic processing and human review at the center of the evidence-analysis process.
